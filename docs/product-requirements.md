# プロダクト要求定義

## プロダクトビジョンと目的

**keygoard** は、TinyGo で書かれたカスタムキーボードファームウェアフレームワークである。

**ビジョン:**
Go 言語でカスタムキーボードを作れる、軽量でわかりやすいファームウェアフレームワークを提供する。

**目的:**
- RP2040 ベースのカスタムキーボードを TinyGo で動かすための土台を提供する
- 「最小構成から実機動作確認しながら段階的に積み上げる」開発スタイルで信頼性を確保する
- v0.1.0 で発生した「USB HID として認識されない」問題をゼロベース再設計で解消し、確実に動く実装を確立する

---

## ターゲットユーザーと課題・ニーズ

### ターゲットユーザー

| ユーザー | 説明 |
|---|---|
| DIY キーボードビルダー | RP2040 ベースの自作キーボードを作りたい。ハードウェアは用意済み、ファームウェアを書きたい |
| Go / TinyGo 開発者 | C 言語（QMK/ZMK）ではなく Go で組み込みを書きたい |
| 組み込み入門者 | マイコンの入門として、使い慣れた Go 言語でキーボードを作りたい |

### 課題・ニーズ

| 課題 | ニーズ |
|---|---|
| QMK / ZMK は C/C++ ベースで学習コストが高い | Go 言語で書けるキーボードファームウェアが欲しい |
| TinyGo 向けのキーボードフレームワークが存在しない | TinyGo の制約に配慮した設計のファームウェアが欲しい |
| 自前 HID 記述子の実装は複雑でバグが出やすい | TinyGo 標準の `machine/usb/hid` を正しく使うだけで動くフレームワークが欲しい |
| 機能を一気に実装すると何が原因かわからなくなる | フェーズごとに実機確認しながら積み上げられる構造が欲しい |

## 成功の定義

### プロダクト全体

- TinyGo で書かれたファームウェアで RP2040 が USB キーボードとして OS に認識される
- 各 Phase の実機確認が完了してから次 Phase に進む
- RAM 使用量 128KB 以下で動作する

### Phase 1（最初のマイルストーン）

| 指標 | 基準 |
|---|---|
| ビルド | `tinygo build -target=waveshare-rp2040-zero` がエラーなく成功する |
| OS 認識 | macOS の USB Prober / System Information にキーボードデバイスとして表示される |
| キー入力 | 物理キーを押すと対応する文字がテキストエディタに入力される |
| デバウンス | チャタリングによる誤入力が発生しない |
| テスト | `go test ./keycode/... ./matrix/...` が全てパスする |

---

## ビジネス要件

- オープンソースとして公開・開発する（ライセンス方針は別途決定）
- RP2040（Waveshare RP2040-Zero）を第一ターゲット MCU とする
- テスト実機は zero-kb02（sago35/keyboards）を使用する
  - リポジトリ: https://github.com/sago35/keyboards/tree/main/zero-kb02
  - 別ファームウェアで動作確認済みのため、開発中のエラーはファームウェアの問題として扱う
- サードパーティパッケージの追加は事前にユーザー確認を必須とする（`tinygo-org/drivers` は許可済み）

## ユーザーストーリー

### Phase 1

1. **キーボードとして認識される**
   - zero-kb02 を Mac に USB 接続したとき、macOS の「システム情報」や USB Prober にキーボードデバイスとして表示される。

2. **キーが打てる**
   - キーマトリクス上の物理キーを押すと、対応する HID キーコードが OS に届き、テキストエディタ等で文字として入力できる。

3. **チャタリングが除去される**
   - 物理キーの接触ノイズによって誤った文字が入力されない。

### Phase 2 以降

4. **レイヤーを切り替えられる**
   - MO キーを押している間、別レイヤーのキーコードが有効になる。
   - TG キーでレイヤーをトグルできる。

5. **タップとホールドで動作が変わる**
   - LT キーを短く押すと通常キーとして、長押しするとレイヤー切り替えとして動作する。

6. **エンコーダーが使える**
   - ロータリーエンコーダーを回すと、割り当てたキーコード（例: 音量調整）が送信される。

## 機能要件

### Phase 1: 最小 HID キーボード

- COL2ROW 方式でマトリクス（3 行 × 4 列）をスキャンできること
  - Col: GP5, GP6, GP7, GP8（出力）
  - Row: GP9, GP10, GP11（入力、プルダウン）
- カウンタ方式デバウンス（閾値 5 サイクル以上で確定）を実装すること
- TinyGo 標準の `machine/usb/hid` を使って 6KRO キーボード HID を実現すること
- レイヤー 0 のみの固定キーマップ（3×4）を持つこと
- USB エニュメレーション完了まで（起動後 500ms）キースキャンを開始しないこと

### Phase 2: レイヤーシステム

- 最大レイヤー数は設計時に定数で決定すること
- MO: ホールド中のみ指定レイヤーを有効にする
- TG: 押下のたびにレイヤーをトグルする
- KC_TRNS: 現在レイヤーに割り当てなしの場合、下のレイヤーを透過参照する
- TT / LT: タップ（短押し）とホールド（長押し）で異なる動作をする

### Phase 3 以降

詳細は [ROADMAP.md](../ROADMAP.md) を参照。

## 非機能要件

### パフォーマンス

- スキャンループ周期: 1ms（1kHz）
- ホットパス（スキャンループ内）でヒープ割り当てを発生させないこと
  - `append` による再割り当て禁止
  - 固定サイズ配列を使用し、スライスの初期確保は初期化時に行うこと

### メモリ

- RAM 使用量: 128KB 以下

### 信頼性

- デバウンス処理が有効であること（チャタリングによる誤入力が発生しないこと）
- 各フェーズの実機確認が完了してから次フェーズへ進むこと

### 保守性

- `machine` 非依存ロジック（keycode / debounce / layer）にはユニットテストを書くこと
- パッケージ間の循環依存を禁止する
- 各パッケージに対応する `docs/packages/*.md` を実装と同時に更新すること

### TinyGo 制約（必須）

- `reflect` パッケージを使用しないこと（TinyGo でランタイムエラーになる）
- `fmt.Sprintf` / `fmt.Printf` を使用しないこと（ヒープ割り当てが大きい）
  - デバッグ出力は `println()` のみ使用する
- `net` / `os` など TinyGo 未対応の標準ライブラリを使用しないこと
- goroutine を多用しないこと（メインループは 1 goroutine で動かす）
- 自前 HID 記述子を書かないこと（TinyGo 標準の `machine/usb/hid` を使う）
- Composite HID は Phase 6 まで追加しないこと

### 対応環境

- ターゲット MCU: RP2040（Waveshare RP2040-Zero）
- TinyGo ターゲット名: `waveshare-rp2040-zero`
- 動作確認 OS: macOS（主）、その他 OS は将来対応
